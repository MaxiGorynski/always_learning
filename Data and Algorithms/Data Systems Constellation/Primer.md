# Data Systems Primer

Bitesized definitions for the 80 concepts in `Constellation.html`, grouped by region.

## Storage engines
- **B-Tree**: The data structure behind almost every database index. Without an index, finding one row means scanning the whole table. A B-tree keeps keys sorted in a shallow, wide tree of disk pages, so the database can find any key, or any range of keys, by reading just three or four pages, even across billions of rows. It’s the default index in Postgres, MySQL and most relational databases.
- **LSM Tree**: A storage design built for heavy write traffic. Instead of finding each record on disk and updating it in place (slow, random I/O), an LSM tree collects writes in memory and periodically writes them out as sorted files that are never modified again. Writes become fast sequential appends; the trade-off is that a read may have to check several files. It powers Cassandra, RocksDB and other write-heavy stores.
- **Write-Ahead Logging (WAL)**: How databases avoid losing data when they crash. Before changing the actual data files, the database first appends a record of the change to a log on disk. If the power cuts out halfway through an update, the database replays the log on restart and finishes or undoes the work. This is what makes ‘committed’ mean durable, and the same log is reused for replication and backups.
- **Bloom Filter**: A tiny, memory-cheap structure that answers one question: ‘could this item be in the set?’ It replies either ‘definitely not’ or ‘probably yes’, and is only ever wrong in the ‘yes’ direction. Databases use it to avoid expensive disk reads for keys that don’t exist: if the filter says no, the file is skipped entirely.
- **Compaction**: Background housekeeping for LSM-tree databases. Because those databases never overwrite data in place, every update or delete leaves the old version behind in an older file. Compaction periodically merges files, keeps only the newest version of each key, and throws away deleted data. Without it, disk usage would grow forever and reads would slow down as they search more and more files.
- **Database Vacuuming**: Garbage collection for databases like Postgres. When you update or delete a row, Postgres doesn’t erase the old version straight away, because transactions already in progress might still need to see it. Vacuuming later removes those dead versions and frees their space for reuse. If it falls behind, tables bloat, queries slow down, and in extreme cases the database stops accepting writes to protect itself.
- **Write Amplification**: The gap between how much data your application asks to write and how much the database actually writes to disk. Change a 100-byte row and the database may rewrite the whole 8 KB page that holds it, record the change again in the write-ahead log, and rewrite it once more during background maintenance. That multiplier, often 10× to 100×, eats disk bandwidth and wears out SSDs, and it is one of the main trade-offs between storage engines.
- **Checkpointing**: A periodic save point for a database. Changes are first recorded in the write-ahead log and held in memory, and only written to the main data files later. A checkpoint forces all of those pending changes out to the data files and marks the spot in the log. After a crash, the database only replays the log from the last checkpoint rather than from the beginning, so recovery is fast.
- **Columnar Storage**: Storing a table column by column instead of row by row. Analytics queries such as ‘average order value last year’ read one or two columns across millions of rows. A columnar store reads only those columns and skips the rest, and because a column holds similar values it compresses extremely well. That’s why data warehouses are columnar, while apps that fetch whole records use row stores.
- **Secondary Index**: An extra index on a column other than the primary key, so you can find rows by something besides their ID. A users table is organised by user_id, but logins search by email; an index on email turns that into a fast lookup instead of a full table scan. The cost is that every insert or update must also update each index, so more indexes mean slower writes and more storage.
- **Index-Only Scan**: A query the database can answer entirely from an index, without visiting the table at all. Normally an index tells the database where a row lives, and it then fetches the row from the table. If the index already contains every column the query needs (a ‘covering’ index), that second trip is skipped, which can make the query several times faster.
- **Backups vs. PITR**: Two different ways to get data back. A backup is a full copy taken at one moment, so restoring it loses everything written since. Point-in-time recovery (PITR) combines a backup with the continuous log of every change made after it, so you can restore to any exact second, such as one second before someone ran DELETE without a WHERE clause.

## Transactions & isolation
- **ACID**: The four guarantees a database transaction gives you. Atomicity: all of its changes happen, or none do. Consistency: rules like ‘a balance can’t go negative’ hold before and after. Isolation: concurrent transactions don’t trip over each other’s half-finished work. Durability: once committed, data survives crashes. Together they let you write correct code without reasoning about every possible failure.
- **MVCC**: The technique most databases use so that reads and writes don’t block each other. Instead of overwriting a row, the database keeps the old version and adds a new one. Each transaction sees the versions that were committed when it started, so a long-running report reads a stable picture while other users keep writing. The cost is cleaning up old versions later.
- **Snapshot Isolation**: An isolation level where every transaction works from a frozen picture of the database as it was when the transaction began. You never see others’ half-finished changes, and reading the same data twice always gives the same answer. Many databases default to it because it’s fast and intuitive, but it still allows one subtle bug: write skew.
- **Serializability**: The strongest isolation level. The database guarantees the result is the same as if transactions had run one at a time, in some order, with no overlap. Every concurrency anomaly disappears, so you can reason about each transaction as if it were alone. The price is lower throughput, and transactions that sometimes get aborted and must be retried.
- **Dirty Read**: Reading data that another transaction has written but not yet committed. If that transaction then rolls back, you’ve made a decision based on data that never officially existed. It’s the weakest possible guarantee, and almost every database prevents it by default, so you’ll mostly meet it as the first rung on the ladder of isolation levels.
- **Read Skew**: When a transaction reads related pieces of data at slightly different moments and sees a combination that never actually existed. Each value it read was real and committed, but another transaction changed things between the reads. The classic case is checking two bank accounts during a transfer and seeing money missing or duplicated. Snapshot isolation prevents it.
- **Write Skew**: A sneaky concurrency bug. Two transactions read the same data, each makes a decision based on it, and each writes to a different row. Neither overwrites the other, so the database sees no conflict, yet together they break a rule that each on its own would have kept. It slips past snapshot isolation and needs serializable isolation or explicit locks.
- **Phantom Read**: When a transaction runs the same search twice and the second time new rows appear, or rows vanish, because another transaction inserted or deleted matching rows in between. Locking existing rows can’t prevent it, because the new rows didn’t exist yet to be locked. It matters for checks like ‘is this time slot free?’ just before booking it.
- **Optimistic Locking**: A strategy for concurrent updates that assumes conflicts are rare. Instead of locking a record while you work on it, you note its version number, and when you save you tell the database ‘only update if the version hasn’t changed’. If someone else changed it first, your update fails and you retry. There’s no waiting and no deadlock, but many retries if conflicts become common.
- **Pessimistic Locking**: A strategy for concurrent updates that assumes conflicts are likely. You lock the record before reading or changing it, and anyone else who wants it waits until you finish. Nobody can change the data underneath you, which suits contested resources like seats or stock, but waiting transactions reduce throughput and can deadlock.
- **Deadlock**: When two or more transactions are each waiting for a lock the other holds, so none of them can ever proceed. A holds row 1 and wants row 2; B holds row 2 and wants row 1. Databases detect the cycle and kill one transaction so the other can finish, so your application must be ready to retry the one that was killed.
- **Lock Escalation**: When a database decides it is tracking too many small locks and replaces them with one big lock. Locking 10,000 individual rows uses a lot of memory, so the database (notably SQL Server) may lock the whole table instead. That saves memory but blocks everyone else who wanted any row in the table, causing surprise slowdowns and deadlocks.

## Consensus & coordination
- **Distributed Transactions**: A transaction that must change data in more than one database or service and still be all-or-nothing. On a single database this is easy. Across machines, any of them, or the network between them, can fail midway, leaving one side committed and the other not. Protocols like two-phase commit and patterns like sagas exist to handle this.
- **Two-Phase Commit (2PC)**: The classic protocol for committing one transaction across several machines. A coordinator first asks every participant ‘can you commit?’, and each prepares and votes. Only if all vote yes does the coordinator tell them to commit. It guarantees all-or-nothing, but if the coordinator crashes after the vote, participants are stuck holding locks until it comes back.
- **Three-Phase Commit (3PC)**: An attempt to fix two-phase commit’s main flaw: getting stuck when the coordinator crashes. It adds an extra round so participants know enough to finish on their own after a timeout. In theory that removes the blocking. In practice it relies on network delays being predictable, which real networks don’t guarantee, so it is rarely used.
- **Saga Pattern**: A way to run a multi-step business transaction across services without locking everything at once. Each step is a normal local transaction that commits immediately. If a later step fails, the saga runs compensating steps that undo the earlier ones, like a refund that reverses a charge. You give up instant all-or-nothing, but every service stays independent and available.
- **Two Generals Problem**: A classic thought experiment proving that two parties talking over an unreliable network can never be 100% sure they agree. Any message might be lost, so every confirmation needs its own confirmation, forever. It’s why distributed systems rely on timeouts, retries and idempotency instead of perfect certainty.
- **Raft**: A consensus algorithm: a way for a group of servers to agree on the same sequence of changes even when some of them crash. The servers elect one leader, the leader sends every change to the others, and a change counts as committed once a majority have stored it. It was designed to be easier to understand than Paxos, and runs inside etcd, Consul and CockroachDB.
- **Leader Election**: How a group of servers picks exactly one of them to be in charge. Many systems are far simpler when a single node, the leader, makes decisions. The hard part is guaranteeing there’s never more than one leader at a time, even when the network is flaky, and choosing a new one quickly when the current leader dies.
- **Quorum**: The minimum number of servers that must take part in an operation for it to count. If data lives on 3 servers, and writes must reach 2 and reads must ask 2, every read overlaps the latest write on at least one server. Quorums let a system keep working while a minority of servers is down, without returning stale data.
- **Split-Brain**: When a network failure splits a cluster in two and each half believes it’s in charge. Both sides accept writes, so the data diverges and the conflicts can’t be cleanly merged later. It’s one of the most damaging failures in distributed databases, and is prevented by requiring a majority vote (a quorum) before any node can act as leader.
- **Distributed Locking**: A lock shared by processes on different machines, so only one of them does something at a time, such as running a scheduled job. It’s much harder than a local lock: the holder can crash, pause, or lose its network connection while still believing it holds the lock. Safe versions use expiring leases and fencing tokens that reject writes from a stale holder.
- **Idempotency**: An operation is idempotent if doing it twice has the same effect as doing it once. Setting a value to 5 is idempotent; adding 5 isn’t. Networks force you to retry requests when you can’t tell whether they succeeded, and idempotency is what makes those retries safe, for example so a payment isn’t charged twice.
- **Exactly-Once Semantics**: The guarantee that each message is processed exactly once, never lost and never duplicated. Networks can’t actually deliver that: you either risk losing messages or risk sending some twice. So exactly-once systems deliver at least once and then discard duplicates, or make processing idempotent, so the effect is as if each message arrived once.

## Replication & consistency
- **CAP Theorem**: A rule about distributed databases. When the network between servers breaks (a partition), you must choose between consistency, where every read sees the latest write and some requests get refused, and availability, where every request gets an answer that might be out of date. You can’t have both during a partition, and that choice frames every replicated database.
- **Strong Consistency**: The guarantee that once a write is confirmed, every later read, from anywhere, sees it. The system behaves as if there were just one copy of the data. It’s the easiest model to program against, but keeping replicas in lockstep needs coordination between servers, which adds latency and can reduce availability.
- **Eventual Consistency**: The guarantee that if writes stop, every replica will eventually hold the same data. Until then, different readers may see different, possibly outdated, values. It keeps systems fast and available, even across regions and network failures, at the cost of occasional stale reads that your application has to tolerate.
- **Consistent Reads**: A practical middle ground between strong and eventual consistency: specific promises about what a reader will see. The most useful are read-your-writes (you always see your own changes) and monotonic reads (data never appears to go back in time). They fix the most confusing user-facing symptoms of replica lag without the full cost of strong consistency.
- **Leader–Follower Replication**: The most common replication setup. One server, the leader, accepts all writes and records them in a log. The others, followers, copy that log and apply the same changes, so each holds a full copy of the data. Followers can serve reads and take over if the leader dies. Postgres, MySQL and MongoDB all work this way by default.
- **Multi-Leader Replication**: A replication setup where more than one server accepts writes, each passing its changes to the others. Each region or data centre can write locally for low latency and keep working if another site is cut off. The catch: two leaders can change the same record at the same moment, and those conflicts have to be detected and resolved.
- **Read Replicas**: Extra copies of a database that only serve reads. All writes still go to the primary, which streams its changes to the replicas. Most apps read far more than they write, so sending reads to replicas multiplies read capacity. The catch is lag: a replica can be slightly behind, so a user might not see a change they just made.
- **Physical Replication**: Replicating a database by copying the exact low-level changes to its storage files, byte for byte. The replica becomes an identical clone of the primary, which makes it simple and dependable for failover. The limits: both servers must run the same database version, and you can’t replicate only some tables or send the data to a different kind of system.
- **Logical Replication**: Replicating a database by sending a stream of row-level changes, such as ‘insert this row’ or ‘update that column’, instead of raw storage bytes. Because it describes changes logically, you can replicate just some tables, replicate between different database versions, or feed the changes into another system entirely. It’s also the foundation of change data capture.
- **Geo-Replication**: Keeping copies of your data in several geographic regions. Users read from a nearby copy, so responses are faster, and if a whole region goes down the others carry on. The hard part is writes: keeping regions in sync means either waiting on slow cross-region round trips, or accepting that regions briefly disagree.
- **Read Repair**: Fixing out-of-date replicas as a side effect of reading. When a read asks several replicas for a value and notices one returned an older version, the system sends the newest version back to that replica. Data that is read often heals itself over time, which keeps leaderless databases like Cassandra converging.
- **Change Data Capture (CDC)**: Streaming every insert, update and delete from a database to other systems as it happens. Instead of other services polling the database, or the app writing to two places, CDC reads the database’s own change log and publishes each change as an event. It’s how search indexes, caches, warehouses and other services stay in sync with the source of truth.
- **Failover**: Automatically switching to a backup server when the primary fails. The system notices the primary has stopped responding, promotes a replica to be the new primary, and redirects traffic to it. Done well, it takes seconds. Done badly, it loses recent writes or leaves two servers both believing they’re in charge.
- **High Availability**: Designing a system to keep running when parts of it fail. That means no single point of failure: redundant servers, replicated data, health checks and automatic failover. Availability is measured in ‘nines’: 99.9% allows almost 9 hours of downtime a year, and 99.99% allows under an hour.

## Partitioning & scale
- **Horizontal Scaling**: Handling more load by adding machines rather than buying a bigger one. A single server has a ceiling and is a single point of failure; ten servers sharing the load can keep growing and survive one dying. It’s easy for stateless app servers behind a load balancer, and much harder for databases, which need sharding or replication.
- **Database Sharding**: Splitting one large database into smaller, independent pieces called shards, each on its own server and holding a subset of the rows. A shard key, such as user ID, decides which shard each row lives on. Sharding lets data and write traffic grow beyond one machine, but queries that span shards get harder, and choosing the key well is critical.
- **Hash Partitioning**: Deciding which partition a record belongs to by hashing its key and using the result to pick a partition. A good hash spreads keys evenly, so no partition gets overloaded. The trade-off is that hashing scrambles key order, so a query over a range of keys, such as all of last week’s orders, has to ask every partition.
- **Range Partitioning**: Deciding which partition a record belongs to by key range: A–F on one server, G–M on the next, and so on. Keys stay in order, so a range query like ‘all events between 9 and 10am’ hits one or two partitions. The risk is hotspots: if the keys are timestamps, every new write lands in the newest range on a single server.
- **Consistent Hashing**: A way of assigning keys to servers so that adding or removing a server moves only a small fraction of the data. Keys and servers are both placed on a circle by their hash, and each key belongs to the next server round the circle. With naive ‘hash mod N’, changing N reshuffles nearly every key; consistent hashing moves only about 1/N of them.
- **Hot Partition**: A partition that gets far more traffic than the others, so it becomes the bottleneck while the rest of the cluster sits idle. It usually comes from one popular key, like a celebrity’s profile, or a key pattern that concentrates writes, like timestamps. Adding servers doesn’t help, because the load is stuck on that one partition.
- **Data Skew**: When data isn’t spread evenly across keys or partitions, so some hold far more than others. Real data is usually lopsided: a few customers, countries or products dominate. Skew causes overloaded partitions, parallel jobs where one task runs for hours while the rest finish in minutes, and query plans built on wrong assumptions.
- **Resharding**: Changing how data is split across shards on a running system, for example going from 4 shards to 16 as data grows. Rows must move between servers while the application keeps reading and writing them, with no data lost and minimal downtime. It’s one of the riskiest operations in a sharded system, so good designs make it rare or cheap.
- **Rebalancing**: Moving partitions between servers so each carries a fair share of data and traffic. It’s needed when servers are added or removed, or when some partitions grow faster than others. A good rebalancing scheme moves as little data as possible and keeps serving requests while the move happens.
- **Federation**: Splitting databases by function instead of by rows: one database for users, another for orders, another for products, often each owned by a different service. Each database is smaller and can be tuned and scaled independently. The cost is that queries and transactions spanning several of them must be stitched together in application code.
- **Data Locality**: Keeping data close to where it’s used. That means storing records that are read together in the same place (the same partition or row), and running computation on the machine that already holds the data instead of shipping it across the network. Network hops are expensive, so good locality makes queries and jobs dramatically faster.

## Traffic & resilience
- **Load Balancing**: Spread requests across instances.
- **Caching**: Keep hot data in faster storage; invalidation is the hard part.
- **Rate Limiting**: Cap requests per client per time window.
- **Backpressure**: Downstream tells upstream to slow down.
- **Circuit Breaker**: Stop calling a failing dependency; fail fast, probe later.
- **Retry Storm**: Mass retries pile load onto an already struggling service.
- **Thundering Herd**: Many clients wake at once and stampede a resource.
- **Connection Pooling**: Reuse open DB connections instead of opening one per request.
- **Connection Multiplexing**: Many logical streams share one physical connection.
- **Connection Leaks**: Connections borrowed and never returned until the pool runs dry.

## Modeling & querying
- **Normalization**: Each fact stored once; no redundancy.
- **Denormalization**: Duplicate data to avoid joins; faster reads, harder writes.
- **Materialized Views**: Precomputed query results stored as a table.
- **Denormalized Read Models**: Query-shaped projections built from the write side (CQRS).
- **Event Sourcing**: State is an immutable log of events; current state is a replay.
- **Schema Evolution**: Changing schemas while old and new readers and writers keep working.
- **Data Warehouse**: Central store built for big analytical queries.
- **Query Planner**: Turns SQL into an execution plan.
- **Cost-Based Optimization**: Estimates each candidate plan's cost from statistics; picks the cheapest.
